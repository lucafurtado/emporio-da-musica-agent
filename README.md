# Empório da Música — Virtual Customer Service Agent (Rico)

Technical case for the **AI Engineer — Full-Stack for Generative AI Applications** position at
[Artefact](https://www.artefact.com/).

A text-based customer service agent, in Python, for **Empório da Música**, a fictional musical
instrument store in Campo Grande/MS, Brazil. The agent answers based on the store's real
operational data (CSVs for products, orders, customers, and promotions) and on the store's
policy manual (PDF), deciding on its own when to query each source.

## How to run

### 1. Requirements

- Python 3.11+
- An [Anthropic](https://console.anthropic.com/) (Claude) API key

### 2. Install

```bash
git clone https://github.com/lucafurtado/emporio-da-musica-agent.git
cd emporio-da-musica-agent
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### 3. Configure

```bash
cp .env.example .env
```

Edit `.env` and fill in `ANTHROPIC_API_KEY` with your key. The key is **never** committed — `.env`
is in `.gitignore`.

### 4. Run the chat (CLI)

```bash
python main.py
```

This starts a new session (ID generated automatically). To resume a saved conversation:

```bash
python main.py --sessao <session-id>
python main.py --listar-sessoes   # lists saved sessions
```

Type `sair` to exit.

### 5. (Optional) Web interface with Streamlit

```bash
streamlit run streamlit_app.py
```

## Architecture

```
emporio-da-musica-agent/
├── data/                    # CSVs and PDF provided by the case (unmodified)
├── src/
│   ├── config.py             # environment variables and paths
│   ├── data_loader.py        # loads and cleans the CSVs with pandas
│   ├── tools.py               # functions the agent can call (function calling)
│   ├── policies.py            # extracts text from the policies PDF
│   ├── llm_client.py          # thin wrapper around the Anthropic SDK
│   ├── agent.py                # persona, system prompt, and tool-use loop
│   ├── history.py              # conversation history persistence (SQLite)
│   └── cli.py                  # command-line interface
├── examples/                 # real conversations generated by the agent
├── main.py
└── streamlit_app.py           # optional web interface
```

**Message flow:**

1. The user sends a message in the CLI.
2. `agent.py` builds the request: system prompt (persona + full policies text) + session history +
   the 3 available tools.
3. Claude decides whether to answer directly or call a tool (`buscar_produtos`,
   `consultar_pedido`, `listar_promocoes`).
4. If it calls a tool, Python executes the function against the cleaned data (pandas) and returns
   the result for the model to continue.
5. The loop repeats until the model has enough information to answer in text.
6. The full conversation (user messages, assistant messages, and tool results) is saved to the
   session's SQLite database.

## Technical decisions and justifications

### Agent framework / approach: hybrid with function calling

I considered three approaches (based on the characteristics of the data) before deciding:

- **SQL agent / pure pandas-agent** (the LLM generates code/queries): discarded because it gives
  the model too much freedom over sensitive data (price, stock). A code-generation error could
  return a wrong number with no signal that anything went wrong.
- **RAG over the CSVs** (indexing rows as text and searching by similarity): discarded because the
  data is structured and small (65 products, 20 orders) — a pandas filter is more precise, cheaper,
  and 100% deterministic than approximate semantic search.
- **Function calling** (chosen): the LLM only decides *when* and *with which arguments* to call a
  deterministic Python function. The model never sees the raw table nor does price math itself — it
  only reads the already-computed result. This eliminates the entire category of "the LLM
  hallucinated a price" errors.

### Policies: full text in the prompt, no RAG

I measured the extracted PDF (`pypdf`): **~11,400 characters / ~2,850 tokens**, 8 short pages. At
this size, implementing RAG (chunking + embeddings + vector search) would be complexity without
benefit — the whole document comfortably fits in the system prompt, with no meaningful cost and no
risk of poor chunking splitting a rule in half (e.g. separating an exception's condition from the
main rule). If the manual had hundreds of pages, the decision would be different.

### Model and provider: Anthropic Claude, `claude-haiku-5-5`

I chose Anthropic because it's the provider I know best day-to-day (I also used Claude Code to
build this project — see the section below), which gives me more control over the agent's behavior
and makes it easier to debug prompting/tool use.

Within the Claude family, I picked **Haiku** over Sonnet/Opus: the LLM's job here is narrow —
deciding which tool to call, with which arguments, and drafting a short reply in a closed domain
(one store, three tools, an 8-page manual). There's no heavy analytical reasoning that would
justify a bigger model; Haiku delivers this with much lower latency and cost. The model is
configurable via `ANTHROPIC_MODEL` in `.env`, in case it needs to change without touching code.

### Prompting strategy

The system prompt has three layers, in a deliberate order:

1. **Persona** (who Rico is, tone): short, informal-but-professional, chat-length replies —
   steers *how* the agent talks, not what it's allowed to do.
2. **Seven numbered hard rules** ("REGRAS QUE VOCÊ NUNCA PODE QUEBRAR"): never invent
   price/stock/order data, confirm identity before revealing order details, the store's
   catalog scope, when to refuse, when to escalate to a human, and how to present promotions.
   These are phrased as explicit, enumerable constraints rather than a vague "be helpful and
   accurate" — a numbered list is something the model can check itself against, and something a
   reviewer can audit rule-by-rule.
3. **The full policy manual text**, appended last, as the single source of truth for anything
   the seven rules point to but don't spell out (exact deadlines, fees, exceptions).

I put the hard rules *before* the policy text on purpose: the rules are short, behavioral, and
need to dominate the model's attention regardless of where in a long policy document the
relevant clause sits. If a future version needed many more rules, I'd watch for prompt bloat and
consider moving some of this logic into tool-level validation instead of prose.

### Tool-use loop: manual instead of the SDK's Tool Runner

The Anthropic SDK offers a "Tool Runner" that automates the tool-call loop, but it's a **beta**
feature. I chose to write the loop manually (a `while` checking `stop_reason`) because it's
simpler to explain and debug in a technical interview, and doesn't depend on an experimental SDK
feature.

### Interface: CLI (+ optional Streamlit)

The case brief is explicit: "the focus is the agent working correctly." I prioritized the agent,
the tests, and the README, and only afterward (since time allowed) built a Streamlit layer on top
of the same `Agente` used by the CLI — zero duplicated logic.

### History persistence: SQLite per session

Each conversation has a `sessao_id` (UUID). I chose SQLite over a per-session JSON file because:
(1) it avoids a race condition if two sessions write at the same time; (2) it's already set up for
queries (`--listar-sessoes`) with no extra code; (3) for the volume of a small store, a local
`.sqlite3` file is enough, with no extra infrastructure needed.

### Data treatment

- `specs` in `products.csv` is a JSON string — parsed into a dict on load.
- `price_brl`, `total_brl`, and dates (`created_at`, `order_date`, `estimated_delivery`) normalized
  to the correct types with `pandas.to_numeric` / `pandas.to_datetime`.
- `category_id` resolved to the category name via a merge with `categories.csv`.
- Derived field `disponibilidade`: a product with `status="active"` and `stock_quantity=0` is
  treated as **currently unavailable** (neither "out of catalog" nor "available") — the store
  policy explicitly asks to never confirm availability without checking current stock.
- **Product `description` is dropped from the catalog exposed to the agent.** For many of the
  "generic" products (ids 131–144 — guitars, basses, drums, keyboards), the `description` text does
  not match the product's real `name`/brand (e.g. a product named "Music Man Bass 1X" with a
  description describing a "Fender Jazz Bass"). On the principle of never exposing to the customer
  information that might be wrong, I only use the reliable structured fields (`name`, category,
  `specs`, price, stock) in tool responses.
- Promotions: only `is_active=True` is considered; the final price is always computed together with
  the list price and the discount percentage (never an isolated number), per the manual's
  transparency policy.

### Guardrails implemented

- **Never invent transactional data**: the system prompt explicitly forbids the model from
  answering price/stock/order status without having called the corresponding tool.
- **Order status only after identity confirmation**: `consultar_pedido` requires
  `confirmacao_cliente` (name or phone) and checks it against the customer record before returning
  any detail — if it doesn't match, the tool returns an error and instructs the model to ask for
  confirmation again, without leaking any order data.
- **Store scope**: the system prompt instructs the agent to politely decline requests for
  accessories (strings, cables, picks, pedals, amplifiers, cases — the store doesn't sell these,
  per the manual) and any topic outside the store's domain.
- **Human escalation**: for decisions the manual doesn't clearly cover, or policy exceptions, the
  agent is instructed to say it will escalate to a human attendant instead of inventing an answer.

## Assumptions made

- The case brief suggests `buscar_produtos` with "name/category/max price" filters — I implemented
  exactly those three filters, plus an optional `somente_disponiveis` flag.
- Since the case doesn't define which customer data point should be requested to confirm an order,
  I assumed full name **or** registered phone number (either one), following the spirit of
  "confirm a customer data point" without being unnecessarily bureaucratic.
- The recruiting email asked for submission via Google Forms (PDF, in English); the case's PDF
  brief asked for a reply by email with the repository link. I followed the email's instructions
  (more specific to this process) and prepared a short text for the form/email with the repository
  link.

## Known limitations and what I'd do with more time

- **No response streaming**: the CLI waits for the full response before printing. With more time,
  I'd implement streaming to reduce perceived latency.
- **No automated tests (pytest)**: given the deadline, I tested the data functions manually and ran
  real conversations end-to-end (see `examples/`). With more time, I'd write unit tests for
  `tools.py` (edge cases: out-of-stock product, wrong identity on an order, nonexistent category)
  and a small eval set of expected question/answer pairs for the agent.
- **Name/category search is simple substring matching**: it doesn't handle typos or synonyms (e.g.
  "guitarra" vs. "violão" if the customer mixes terms). A reasonable next step would be to
  normalize accents/plurals or use a light fuzzy match (e.g. `rapidfuzz`).
- **No rate limiting / abuse protection** in the CLI — acceptable for a prototype, but necessary
  before going to production (e.g. behind the WhatsApp Business API).
- **Minimal observability**: there's no structured logging of tool calls or token usage metrics.
  With more time, I'd add structured logs (each tool_use, its input, and result) to make production
  debugging easier.
- **Small, static catalog**: for the store's real volume (300+ products per the manual), it would
  be worth revisiting whether a simple pandas filter is still enough, or whether it would pay off to
  index into a database with full-text search.

## AI coding assistant usage (Claude Code)

I used **Claude Code** (Anthropic) from start to finish on this case, deliberately dividing who
decides what:

- **I defined**: the architecture (hybrid with function calling), the persona (Rico), the provider
  and model (Anthropic Claude Haiku), the decision not to use RAG for the policies, the persistence
  strategy (SQLite), and the decision to create the repository/commits at each completed stage.
- **Claude implemented and explained**: it wrote each module's code in stages (data treatment →
  tools → policies → agent → history → CLI), explaining at each stage, in plain language, what it
  did and why, including discarded alternatives (e.g. why not RAG for the CSVs, why a manual loop
  instead of the SDK's beta Tool Runner).
- **I reviewed and tested**: I ran manual tests of the data functions, reviewed the text extracted
  from the policies PDF, and validated the example conversations by running the real agent against
  the live API before including them in the repository.

I found the workflow productive mainly because I forced Claude to work in small, reviewable stages
instead of generating the whole project at once — that made it much easier for me to understand and
be able to explain any part of the code in upcoming technical interviews.

## Example conversations

See the [`examples/`](examples/) folder — 5 real conversations with the agent, covering: product
search by category/price, general store information, a specific product's price, and two distinct
return-policy scenarios applied to real orders: a manufacturing-defect exchange (30-day window) and
a buyer's-remorse / right-of-withdrawal return on an online purchase (7-day window). The store's
policy manual treats these as separate rules, and the agent correctly distinguishes between them
instead of applying one blanket "return policy."
